# Experimento F9: petición duplicada

La misma operación del cliente llega más de una vez: seguida, o tarde, después de otras más nuevas. El [contrato](CONTRACT.md) promete que repetir una operación no tiene efectos adicionales; **no** promete nada sobre el orden, porque las operaciones no llevan ID de petición ni versión. El experimento comprueba lo primero y mide lo segundo.

La predicción se escribió **antes** de las ejecuciones registradas, pero **después** de una ejecución exploratoria, cuyas observaciones se indican.

## Configuración

| Campo | Valor |
|---|---|
| Script | [`experiments/duplicate_requests.py`](../experiments/duplicate_requests.py) |
| Topología | Una sola máquina (WSL2), clúster local de 4 CPU |
| Trabajo | `dup-demo`, carga `ticker`, réplicas de 1 CPU |
| Disparador | El script entrega cada petición las veces indicadas, en el mismo proceso que el dominio; el código del producto no cambia |
| Secuencia | `submit_job` ×2 → `set_replicas(3)` ×2 → `submit_job` con el mismo ID y otra especificación → `set_replicas(4)` y `set_replicas(1)` seguidos → llega tarde la copia de `set_replicas(4)` → `stop_job` ×2 → llega tarde la copia del `submit_job` original |
| Afirmación bajo prueba | Un duplicado inmediato no tiene efecto adicional; una especificación distinta con el mismo ID se rechaza con `JOB_ALREADY_EXISTS`. Un duplicado tardío de `set_replicas` es una petición más y deshace el objetivo nuevo (limitación conocida) |

## Lo observado en la ejecución exploratoria

Todas las comprobaciones se cumplieron. La copia tardía de `set_replicas(4)` devolvió el objetivo a 4 y arrancó 3 intentos nuevos; la copia tardía del `submit_job` no reactivó el trabajo detenido.

## Predicción (antes de las ejecuciones registradas)

1. **`submit_job` duplicado:** un solo trabajo, las dos copias responden `dup-demo` y se crean 2 intentos, no 4.
2. **`set_replicas(3)` duplicado:** un solo cambio de objetivo y un solo intento nuevo.
3. **Mismo ID, otra especificación:** `JOB_ALREADY_EXISTS`, sin ningún cambio.
4. **Tras cada paso**, objetivo, instancias en marcha y actores vivos en Ray coinciden.
5. **La copia tardía de `set_replicas(4)` deshace `set_replicas(1)`:** el objetivo vuelve a 4 y se arrancan 3 intentos nuevos. No hay forma de distinguir una copia tardía de una petición nueva: gana la última en llegar.
6. **La copia tardía del `submit_job` original no reactiva el trabajo detenido**, porque repetir la especificación no restablece el objetivo.
7. **Parada limpia.**

## Resultado observado

Tres ejecuciones el 26 de noviembre de 2026, Ray 2.58.0, Python 3.12.3, WSL2. **7 de 7 comprobaciones en las tres.** Evidencia: [`evidence/`](evidence/), `f9_run1..3.json`.

Las tres ejecuciones dieron exactamente los mismos valores:

| Paso | Respuestas | Objetivo | Actores vivos en Ray | Intentos creados por el paso |
|---|---|---|---|---|
| `submit_job` ×2 | `dup-demo`, `dup-demo` | 2 | 2 | 2 |
| `set_replicas(3)` ×2 | 3, 3 | 3 | 3 | 1 |
| Mismo ID, otra especificación | `JOB_ALREADY_EXISTS` | 3 | 3 | 0 |
| `set_replicas(4)` y `set_replicas(1)` | 4, 1 | 1 | 1 | 0 |
| Llega tarde la copia de `set_replicas(4)` | 4 | **4** | 4 | **3** |
| `stop_job` ×2 | 0, 0 | 0 | 0 | 0 |
| Llega tarde la copia del `submit_job` original | `dup-demo` | 0 | 0 | 0 |

## Conclusión

- **Los duplicados inmediatos no tienen efecto adicional**, como promete el contrato.
- **Los duplicados tardíos sí lo tienen, cuando llegan después de una petición más nueva.** Una copia tardía de `set_replicas(4)` deshizo un `set_replicas(1)` posterior y arrancó 3 procesos que ya nadie pedía. El dominio no puede distinguirla de una petición nueva: gana la última en llegar.
- **En esta fase el riesgo no existe en la práctica**, porque el cliente llama al dominio en el mismo proceso y nada puede reordenar las peticiones. Con transporte real sí existirá.
- **`submit_job` es seguro también tarde:** repetir la especificación nunca cambia el objetivo, así que no reactiva un trabajo detenido.

## Qué implica para la versión nativa

- **Las operaciones que cambian el objetivo necesitan un orden comprobable**: por ejemplo, que el cliente envíe la versión del objetivo que leyó (escritura condicional, "si la versión sigue siendo v") o un número de secuencia por cliente, y que el controlador rechace lo que llegue fuera de orden.
- **Si el estado del controlador se replica**, ese orden debe ser el mismo en todas las réplicas; es la misma decisión que la de dónde y cómo se confirman las escrituras.

## Alcance de la evidencia e incertidumbre

- Los duplicados y el reordenamiento se producen en el script, en el mismo proceso que el dominio; no hay red que los cause. El experimento mide lo que haría el dominio si le llegaran.
- No se prueban clientes concurrentes.
